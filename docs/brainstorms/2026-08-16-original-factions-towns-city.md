## 背景与目标

《蛋蛋江湖 2.0》当前势力页已具备悬榜、贡献、武学学习和招募等可玩链路，城市页则仅开放按本卷货币招募侠客的酒馆。下一阶段需要以本机《诸天刷宝录》原版资源与运行时事件为唯一真值，完整复刻以下三套相互关联但语义不同的系统：

1. 势力：组织资料、解锁、贡献、声望及相关功能入口。
2. 位面城镇：位面主城、公共场所和正式势力城镇。
3. 现世城市经营：土地、城市建设、公司、产业建筑和长期经营。

“完整复刻”指数据、文案、关联、解锁、资源、公式、状态变化和交互闭环完整，不等同于照搬原版像素布局。无原版证据的内容不得猜测或用近似规则补齐。

- `shili.json` 为 `43 × 26 × 1`，含 1 条空记录和 42 条非空势力记录。

## 核心需求

### 原版证据契约

所有进入实现的内容必须记录来源和证据等级：

- 静态已确认：原版 JSON 表中的 ID、名称、文案和直接关联。
- 运行时已确认：事件表中可定位并复算的公式、解锁和状态变化。
- 待实机核验：仅靠静态资源无法确定的刷新、展示、操作顺序和边界状态。

待实机核验内容必须保留记录并保持未开放，不得生成虚构值或近似实现。

### 身份与关系契约

- 统一定义位面、主城、场所、势力、势力城镇、建筑、科技、职位、角色、资源和场景功能。
- 原版数字 ID 必须保留为可追溯的 `sourceId`；项目运行时可以继续使用稳定类型 ID。
- 开发前形成以下关系的完整清单：
  - 位面 → 主城 → 公共场所；
  - 位面 → 势力 → 势力城镇；
  - 场所 → 原版场景功能；
  - 建筑 → 职位 → 能力加成 → 产出；
  - 科技 → 解锁条件 → 建筑或功能；
  - 资源 → 来源 → 消耗入口。
- 页面不得自行拼装或复制实体关系。

### 资源与进度契约

- 统一管理位面货币、势力贡献、声望、现金和经营资源。
- 统一处理势力解锁、城镇开放、科技解锁、建筑开放、城市等级和发展度。
- 招募、学习、兑换、建造和经营结算必须调用统一 Domain action。
- UI 只展示状态和触发 action，不直接修改资源或重复计算公式。

### 城市经营状态契约

新存档必须覆盖：

- 土地、城市地面和地块所有权；
- 已建、在建和迁移中的建筑；
- 城市属性、等级、发展度和扩建状态；
- 公司、资产、职位任命、财务、租金和收支；
- 科技、生产队列、材料池、派遣队伍及各产业队列；
- 所有队列的剩余时间和可原子结算状态。

## 页面信息架构

江湖侧栏采用四入口分离：

```text
江湖
├─ 关卡
│  └─ 位面战斗与推进
├─ 势力
│  ├─ 势力档案、介绍和解锁状态
│  ├─ 贡献、声望及等级
│  └─ 任务、武学、兑换、招募的总览和快捷入口
├─ 城镇
│  ├─ 位面主城
│  │  └─ 官府、商店、酒馆、武馆、铁匠铺等公共场所
│  └─ 势力城镇
│     └─ 阵营任务、技能学习、贡献兑换、势力招募
└─ 城市
   ├─ 城市地图、地面与土地
   ├─ 公司总览、资产、职位和财务
   ├─ 建造、升级、扩建与迁移
   └─ 各产业建筑的专属功能
```

页面行为约束：

- 势力页继续承担高保真总览，但任务、学习、兑换和招募不复制第二套业务逻辑。
- 势力页快捷入口和城镇页场所入口打开同一个功能模块，共享状态与 Domain action。
- 返回时恢复来源页面以及原来的位面、势力和场所选择。
- 城镇跟随当前选择的位面；现世城市经营是跨位面的独立系统，不随当前位面切换。
- 未解锁场所可以展示，但必须使用原版解锁条件和玩家可理解的原因，禁止提前操作。

## 视觉方向

采用“原版信息架构 + 当前视觉体系”：

- 保留原版场所入口、功能层级、信息顺序和交互关系。
- 延续《蛋蛋江湖 2.0》现有水墨、纸张、牌匾和卷轴语言。
- 不要求像素级复刻原版 Construct UI。
- 页面需适配桌面与移动端，复杂城市地图不得依赖只能在桌面使用的 hover 操作。
- 面向玩家的 UI 不展示内部 ID、Action 名称或错误码。

## 存档与兼容性

- 城市经营接入时创建全新的存档版本和 save key。
- v17 旧档不迁移、不覆盖，也不补发任何城市经营历史收益。
- 旧档保留在本机，但不能用于新版本继续游戏。
- 删除新档只删除新 save key，不应顺带删除旧版本存档。
- 新档按原版城市初始状态创建。
- 损坏存档、并发写入冲突和外部删除仍需维持现有安全边界。

## 计时模型

- 项目建设、生产、修习、驯养、教育和派遣只在游戏运行期间推进。
- 关闭游戏后暂停；重新载入时恢复剩余时间，不补算离线产出。
- 使用统一的单调运行时钟，不允许各建筑自行读取系统时间推进状态。
- 浏览器后台节流恢复后，只补仍在运行期间真实经过的时间。
- 建造完成、队列结算、租金扣除和资源产出必须作为原子操作写入存档。
- 原版周期、速度加成和结算顺序逐项复算，不使用统一近似值。
- 势力任务刷新使用相同的运行时原则，不产生离线换榜或离线领奖。

## 方案与决策

### 决策标准

- 原版内容全量、可追溯且可复算。
- 避免后期反复修改共享 ID、资源和存档结构。
- 每个阶段能形成可运行、可验证的闭环。
- 不因追求原版完整性破坏当前项目的一致视觉和安全边界。

### 选定方向

采用“共享契约先行、系统纵向交付”：先冻结跨系统身份、关系、资源、解锁和存档边界，再按依赖顺序逐个系统完成原版证据、Domain、页面和验证。

### 选择理由

该范围横跨势力、位面场景、公司、城市、建筑、侠客、装备、灵兽和运行时队列。完全边做边发现会频繁调整存档与关联；开发前穷尽所有 UI 细节又会长期没有可运行成果。先锁定共享契约、再纵向交付，可以兼顾原版准确度和阶段性验收。

### 主要备选

- 系统纵向直接开发：可更快看到页面，但跨系统字段与公式容易返工。
- 全量证据全部解码后开发：确定性最高，但前期研究周期过长，且部分行为仍必须实机核验。

- 清单存在遗漏时不得宣告完整复刻完成。

## 阶段验收门槛

每个纵向阶段必须同时满足：

- 对应范围的原版数据全量录入，而不是仅完成部分位面。
- 公式与解锁条件具有原版证据。
- 数据、Domain、存档、页面和交互形成闭环。
- 单元测试、构建和直接相关的浏览器视觉验证通过。
- 存档创建、恢复、损坏和写入冲突边界得到验证。
- 明确列出仍待实机核验的内容，不以近似实现冒充完成。
- 阶段验证通过后可以独立 Git 提交，再继续下一阶段。

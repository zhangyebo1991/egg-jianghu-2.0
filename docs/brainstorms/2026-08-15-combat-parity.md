# 自动战斗原版全对齐

- 日期：2026-08-15
- 状态：已确认
- 当前项目：`egg-jianghu`
- 参考原版：`D:\Projects\OpenProject\花旦的各种小游戏\挂机游戏\诸天刷宝录`

## 背景与目标

当前战斗虽然部分速度和伤害公式参考了《诸天刷宝录》，但执行模型仍是固定 `100ms` tick：行动条满的单位会在同一 tick 内依次完成技能选择、资源消费、伤害、死亡和战斗结算。`skill-used` 与 `damage` 等事件也会在同一批次交给 UI，视觉效果不会阻塞逻辑。

这造成以下偏差：

- 角色行动频率体感明显快于原版。
- 多名角色可能在同一 tick 内近似同时出手。
- 技能提示、前摇、特效、弹道、受击和收尾不占用实际战斗时间。
- 高倍速只增加逻辑 tick，动画仍以固定时长播放，动作会重叠。
- 波次、胜负和自动重开缺少原版等待阶段。
- 后台补算会压缩演出，进一步提高挂机效率并缩短养成周期。

本次目标是完整重做自动战斗，使战斗规则、结果、时序和视觉演出尽量与原版一致，并使动作演出真实限制挂机效率。唯一明确排除的是音效。

## 已确认范围

### 包含

- 角色和敌人的战斗属性构建。
- 敌人生成、阵型、波次及 Boss 规则。
- 行动值积攒、底部共用行动条和单一行动队列。
- 同时满条时的排队与原版 tie-break。
- 自动技能 AI、目标选择、能量回复、能量消费和技能 CD。
- 命中、闪避、暴击和完整伤害公式。
- 治疗、护盾、吸血、Buff、Debuff、控制、DoT 和 HoT。
- 复活、召唤、多目标、多段、连击和追击。
- 技能提示、角色动作、主特效、弹道、命中、受击、飘字和死亡演出。
- 波次切换、胜负、奖励结算和自动重开时序。
- 四档倍速及窗口失焦、最小化和后台恢复语义。
- 从原版提取并复用战斗视觉素材。

### 不包含

- 音效和音乐。
- 自动/手动模式切换。
- 玩家轮到时手动选择技能。
- 手动“防御”按钮。
- 非战斗任务、门派委托等计时系统。
- 与战斗无关的页面改版。
- 原版不存在的新战斗机制。

若原版自动 AI 本身会选择“防御”，仍需作为自动行动还原，只是不增加手动操作入口。

## 已确认的当前差异

- `COMBAT_TICK_MS = 100`，当前速度公式本身大体接近原版，但缺少原版全局动作锁。
- 当前 `readyOrder()` 会收集同一 tick 内所有满条单位，并在一次逻辑调用中连续执行。
- 当前 `executeAction()` 会立即完成选技能、扣资源、伤害、状态、死亡和结算。
- 当前多段攻击和多目标攻击通过同步循环一次性完成。
- 当前 DoT/HoT、部分增伤乘区、熟练和技能组威力仍存在简化值或占位值。
- 当前敌人波次、成长、阵型和 Boss `3.1` 倍率包含项目自定义规则。
- 当前 UI 将 `skill-used` 与 `damage` 同批呈现，固定 CSS 动画不会约束伤害时点。
- 当前倍速为 `1 / 2 / 4`，只放大逻辑 tick 数。
- 当前波次清空和胜负后会立即进入下一波或重新创建战斗。
- 当前后台恢复最多批量推进 600 个旧式 tick，仍会省略动作实际耗时。

原版则具有递增出手权重、单一行动队列、全局 `战斗暂停`、分阶段演出和命中结算；动作期间行动条、CD、状态和持续效果均暂停。原版战斗倍率为 `1 / 1.8 / 2.6 / 3.6`，统一缩放整个战斗 runtime。

## 方案与决策

### 决策标准

- 能否精确还原行动顺序和命中时点。
- 能否让演出时长真实计入挂机效率。
- 能否在倍速、页面卡顿和后台恢复时保持确定性。
- 能否通过自动测试和原版实机 trace 验证。
- 不为未来需求建立无关框架。

### 选定方向：确定性阶段调度器

战斗使用一个确定性的调度时钟，将每次行动拆成明确阶段和命中节点。逻辑和表现共享同一时间线，表现层不再自行决定伤害时点。

选择理由：

- 能严格保证任意时刻只有一个主动行动链。
- 能精确表达技能提示、前摇、弹道碰撞、多段命中和收尾。
- 能统一缩放逻辑、等待和动画。
- 能让批量推进仍完整计算每段动作耗时。
- 相同输入和 seed 可产生可重复的事件序列。

### 未选方向：逐函数异步移植

按原版 `Wait` 链逐函数翻译虽然便于源码对照，但依赖异步计时器，容易受到页面卡顿、倍速切换和后台限速影响；恢复、测试和确定性也更难保证。因此不作为正式运行架构。

## 调度模型

### 战斗状态

战斗按以下状态推进：

```text
行动积攒 -> 单位行动 -> 波次过渡 -> 战斗结束
```

只有“行动积攒”会推进：

- 角色行动值。
- 技能 CD。
- 时间型 Buff 和 Debuff。
- DoT 和 HoT。
- 召唤物存续时间。

“单位行动”“波次过渡”和“战斗结束”期间均保持全局动作锁，以上系统全部冻结。

### 行动队列

- 单位达到行动阈值时获得递增的 `readySeq` 并进入全局队列。
- 多个单位同一时刻达到阈值时，严格复刻原版遍历顺序分配 `readySeq`。
- 入队后不再按当前速度或超出阈值的行动值重新排序。
- 队首单位完成整个行动链后，才允许下一单位行动。
- 死亡单位取消尚未执行的出手权。
- 复活单位不恢复死亡前遗留的队列位置，具体初始行动值按原版证据处理。
- 召唤物在召唤动作结算完成后入场，最早从下一次积攒阶段开始获得行动值。
- 受控单位满条后的队列处理按各控制类型的原版行为逐项映射。

### 单次行动生命周期

```text
技能判断
-> 技能名提示
-> 起手动作
-> 前摇
-> 主特效或弹道
-> 命中结算
-> 受击与飘字
-> 收尾
-> 解除动作锁
```

调度器生成 `ActionPlan`，记录本次行动的阶段、持续时间和命中节点。`ActionPlan` 不提前计算伤害；命中节点到达时再读取当时有效状态并结算。

## 技能与结算规则

### 行动开始

队首单位通过合法性检查后，按原版顺序处理：

```text
行动值消费
-> 能量回复
-> 自动技能判断
-> 目标选择
-> 能量消费和 CD 设置
-> 生成 ActionPlan
```

需要还原的自动 AI 内容包括：

- 技能优先级和候选顺序。
- 能量、CD 和目标条件。
- 治疗、复活和增益技能的使用条件。
- 无可用技能时的普攻或自动防御行为。
- 随机技能和随机目标的范围及 RNG 调用顺序。

### 单次命中

每个命中节点独立执行原版调用链：

```text
目标复核
-> 闪避判定
-> 暴击判定
-> 伤害公式
-> 护盾扣除
-> 气血扣除
-> 吸血或附带效果
-> Buff/Debuff
-> 死亡处理
-> 命中反馈
```

具体要求：

- 未命中时显示闪避或未命中，不产生仅命中才触发的效果。
- 物理、法术、元素、普攻、技能组、专精、熟练、最终增减伤和受伤加成等全部使用原版公式。
- 保留原版每一步的取整方式、上下限和随机调用顺序。
- 护盾、护盾超限和受护盾效果按原版函数处理。
- 吸血使用原版实际伤害口径。
- Buff 施加时点与原版一致，不统一推迟到整个技能结束。

### 多目标、多段与追击

- 每一段攻击都有独立 `hitAt`。
- 每段独立判断命中和暴击。
- 某段击杀目标后，后续段停止、跳过或重选目标，按对应原版技能处理。
- 群体技能对每个目标分别结算。
- 连击、三连击和目标追击属于同一次动作锁。
- 命中间隔使用技能字段或原版等待值，不使用统一动画时长。

### Buff、Debuff 与持续效果

每个原版状态需要映射：

- 叠层上限、覆盖、共存和刷新持续时间规则。
- 时间型与行动次数型持续方式。
- 中毒、燃烧和恢复的周期与首次触发时点。
- 眩晕、麻痹、冰冻、静止等控制效果。
- 控制抵抗、增益时间和减益时间修正。
- 净化、驱散和死亡后状态保留规则。
- 行动结束消耗与自然时间结束的差异。

动作锁期间状态时间冻结；新施加状态也要等重新进入积攒阶段后才开始走时。

### 复活、召唤与特殊效果

- 复活目标、恢复比例、状态清理、行动值和队列状态按原版处理。
- 召唤数量、阵位、属性继承、召唤强度、持续时间和初始行动值按原版处理。
- 召唤失败仍需完成技能演出，资源是否返还只按原版证据决定。
- 治疗、护盾、能量增加和行动值推进等效果也必须在对应节点生效。

### 随机确定性

- 整场战斗只使用一个确定性战斗 RNG。
- 技能、目标、闪避、暴击和效果概率按原版调用顺序消费随机数。
- UI 粒子和装饰随机不得消费战斗 RNG。
- 相同阵容、状态和 seed 必须产生相同事件顺序和结果。

## 视觉演出

### 逻辑与视觉绑定

| 阶段 | 视觉表现 | 逻辑变化 |
|---|---|---|
| 技能提示 | 显示技能名称并突出行动者 | 不造成伤害 |
| 起手/前摇 | 播放角色动作 | 不造成伤害 |
| 主特效 | 生成技能特效或弹道 | 不提前扣血 |
| 命中 | 弹道碰撞或主特效到达目标 | 执行对应命中结算 |
| 受击 | 受击、闪避、暴击、伤害或治疗飘字 | 展示已经发生的结果 |
| 收尾 | 特效消散、角色归位 | 完成后解除动作锁 |

弹道技能以实际碰撞时点为伤害节点；无弹道技能使用原版主特效的命中时点。

### 战斗渲染层

- 保留当前项目外围导航、收益和战斗日志，只改造战场及直接相关控件。
- 战场使用专用 `requestAnimationFrame` 渲染循环，不引入新的游戏引擎。
- 动画帧由 `phaseElapsed / phaseDuration` 决定。
- 不使用独立 `setTimeout` 或固定 CSS 时长决定逻辑节点。
- 切换倍速时，当前动作立即按新倍率继续，不重播也不跳过命中。
- 停止战斗后不得留下延迟伤害或孤立特效。

### 原版素材

从原版 `package.nw` 中只提取实际使用的战斗素材：

- 角色战斗帧和受击帧。
- 技能主特效。
- 弹道和碰撞特效。
- 技能提示相关 UI。
- 行动条和队列标记。
- 死亡及波次切换素材。

不提取音频，也不导入与战斗无关的整包资源。

素材清单需要记录：

- 原版路径和用途。
- spritesheet 裁切区域。
- 帧数、帧序和单帧时间。
- 原点、锚点、缩放和镜像规则。
- 对应技能或效果编号。
- 动态持续时间字段。

无法直接复用或缺帧的素材必须标为“近似还原”并在交付前确认，不能静默混用。

### 底部共用行动条

- 每个存活单位以头像或标记显示在共用轨道上。
- 标记位置直接对应行动值。
- 满条后进入待行动区域，并按 `readySeq` 展示顺序。
- 当前行动者高亮；动作期间其他标记完全静止。
- 死亡、复活、召唤和退场同步更新标记。
- 个体卡片不再重复显示独立气机条。

## 波次、胜负与自动重开

### 波次切换

```text
最后一次命中
-> 受击与死亡演出
-> 掉落/击杀结算
-> 波次结束停顿
-> 下一波入场
-> 恢复行动积攒
```

- 过渡期间保持动作锁。
- 旧波次死亡演出结束前不能生成新敌人。
- 下一波入场等待使用原版时长。
- 我方气血、能量、护盾、状态、行动值、队列和召唤物的跨波规则逐项对齐原版。
- 禁止最后一击、下一波生成和下一角色攻击出现在同一逻辑调用中。

### 胜负与重开

```text
死亡收尾
-> 胜负演出
-> 奖励与进度结算
-> 原版结束等待
-> 决定下一场
-> 新战斗入场
```

- 驻守、闯荡、胜利推进和失败重整继续保留。
- 奖励入账时点按原版处理。
- 战斗结果确定后禁止残余弹道、旧队列或旧状态继续结算。
- 自动重开必须经过原版等待，不能由 `GameSession.handleResult()` 当场重建战斗。

## 倍速、后台与离线

### 倍速

- 使用原版四档倍率：`1 / 1.8 / 2.6 / 3.6`。
- 同时缩放行动积攒、等待、动作、弹道、特效和飘字。
- 调度器精确推进到下一阶段节点，不能因固定 tick 跨过命中时点。

### 最小化与后台标签页

- Electron 设置 `backgroundThrottling: false`，最小化时仍按真实时间运行完整战斗。
- 浏览器后台受限时允许批量推进，但所有动作阶段和等待仍计入模拟时间。
- 批量推进只省略不可见绘制，不得省略动作耗时或结算节点。
- 返回前台时显示当前真实阶段，不集中重播历史动画。
- 历史奖励和伤害仍按顺序结算且不得重复。
- 移除旧式“批量 tick 后每个行动瞬间完成”的补算路径。

### 休眠、关闭与离线

- 关闭游戏后不继续模拟战斗，不发放离线战斗奖励。
- 操作系统休眠或进程长时间暂停后，不把整个休眠间隔补算为战斗时间。
- 应用正常运行但失焦或最小化时，保持与原版相同的实时效率。
- 非战斗计时系统保持现状。

## 实现边界

仅设置当前需求需要的四层：

- `CombatScheduler`：战斗时钟、阶段、动作锁和行动队列。
- `CombatRules`：原版公式、AI、目标、状态和命中结算。
- `CombatPresentation`：读取调度状态并播放素材，不得反向修改战斗数据。
- `GameSession`：持久奖励、关卡推进、停止战斗和下一场创建。

战斗快照需要包含：

- 当前运行阶段。
- 全局 `readySeq`。
- 待行动队列。
- 当前 `ActionPlan`。
- 当前阶段及阶段内时间。
- 波次和胜负过渡状态。
- 可复现 RNG 状态。

现有存档不保存进行中的战斗，原则上不升级存档结构。英雄、装备、背包和进度保持兼容；只有实现证明必须增加持久字段时，才另行设计迁移。

## 证据与数据要求

实施前建立“战斗对齐矩阵”，每条记录包含：

- 机制或数据项。
- 原版函数、数据字段或实机现象。
- 当前项目对应实现。
- 精确预期结果。
- 自动测试或实机对照片段。
- 已确认、推断或尚缺证据。

原版源码、数据表和实机现象是唯一规则来源。当前项目中无法映射到原版的战斗内容必须列出并确认，不得静默沿用旧公式或猜测 fallback。

## 实施顺序

1. 提取原版规则、时间、技能数据和素材清单，形成对齐矩阵。
2. 建立原版公式与确定性事件序列的 golden fixtures。
3. 实现调度器、动作队列和分阶段 `ActionPlan`。
4. 接入伤害、状态、AI、敌人和波次规则。
5. 接入原版动作、特效、弹道和底部行动条。
6. 改造胜负重开、最小化运行和后台批量推进。
7. 完成原版实机对照后删除旧式即时结算链路。

不在正式运行时长期保留两套战斗模式。旧引擎如需用于差异检测，只能作为实施期间的测试工具。

## 验收标准

只有同时满足以下条件才能称为完成：

- 任意时刻最多一个主动行动链，群体受击演出除外。
- 行动期间所有积攒、CD 和状态时间冻结。
- 伤害、治疗、护盾、复活和召唤只在对应节点生效。
- 当前可参与战斗的技能、Buff、敌人和召唤物均有原版映射。
- 原版公式 fixtures 的整数结果完全一致，包括取整和上下限。
- 相同 seed 的技能、目标、命中、暴击、伤害、死亡及胜负事件序列完全一致。
- 逻辑节点时间精确一致；视觉显示允许最多一帧误差。
- 四档倍率统一缩放完整 runtime。
- 前台、最小化和后台恢复在相同真实运行时间下得到相同战果。
- 关闭或系统休眠期间不产生额外战斗收益。
- 波次和重开等待全部计入挂机效率。
- 不存在旧引擎残留的即时伤害、并发行动或 `100ms × 倍速` 快进路径。

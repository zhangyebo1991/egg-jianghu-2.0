# 新建游戏、玩家角色与删档重开设计规格

## 背景与目标

当前应用启动后会直接通过 `GameSession.create(window.localStorage)` 加载存档；没有存档时则创建一个没有侠客、没有阵容的空白初始状态，导致玩家无法立即开始挂机。

本次改动增加明确的标题页与存档入口，并让新建游戏生成一名可自定义姓名的基础玩家角色。玩家角色自动进入侠客列表及默认阵容，使新档可以直接开始第一关挂机。同时提供安全的删档重开流程。

## 已确认范围

- 启动后始终先显示标题页，而不是自动进入游戏。
- 标题页提供“新建游戏”和“继续游戏”。
- 没有存档时，“继续游戏”保持可见但不可用。
- 新建游戏时只要求填写玩家姓名，不提供职业选择。
- 玩家角色固定为丙级剑客，自动加入侠客列表并放入前排第一个阵容位。
- 旧存档继续加载原有内容，不补发玩家角色，也不迁移成新档结构。
- 已有存档时新建游戏必须经过覆盖确认。
- 游戏内提供“删档重开”，经过二次确认后删除存档并回到新建游戏流程。

## 不在本次范围

- 玩家外观、性别、头像和初始职业选择。
- 为旧存档补发玩家角色或修改已有阵容。
- 多存档槽、云存档或删除后的恢复机制。
- 调整现有酒馆侠客、势力侠客的数值与招募规则。

## 方案选择

采用独立标题页和新建游戏页，并由顶层应用状态控制当前显示“标题”“新建游戏”或“游戏主体”。相比直接使用浏览器 `prompt` / `confirm`，该方案可以延续现有视觉风格，显示明确的校验和错误信息，并能够稳定地进行单元测试与 E2E 测试。

## 启动与页面状态

顶层页面状态包含三种模式：

- `title`：显示标题页和存档入口。
- `new-game`：显示姓名输入与新档创建表单。
- `playing`：显示现有 `renderShell` 游戏主体。

应用启动时只检测 `SAVE_KEY_V10` 是否存在并进入 `title`，不立刻创建或载入 `GameSession`。用户点击“继续游戏”后才从存档创建 session 并进入 `playing`。如果存档在标题页显示后被移除或已损坏，则停留在标题页并提示无法继续，不进入一个隐式空白新档。

点击“新建游戏”进入 `new-game`。如果已检测到存档，姓名提交前显示覆盖警告及确认按钮；取消时返回标题页且不修改存档。

## 玩家角色模型

新增固定内容定义 `hero_player`：

- 品阶：丙。
- 初始职业：`sword`（剑客）。
- 来源：`starter`，不可通过酒馆或势力招募。
- 招募成本：0。
- 所属世界：`world_01`。
- 初始资质：臂力 8、悟性 8、根骨 9、身法 9、定力 8。

`HeroDefinitionV10.source` 扩展为 `'tavern' | 'faction' | 'starter'`。玩家定义加入 `HEROES_V10`，确保现有角色查找、战斗属性计算和侠客详情能够复用同一套内容链路；它不加入 `TAVERN_HEROES` 或 `FACTION_HEROES`，因此不会出现在招募列表。

`HeroProgressV10` 新增可选字段 `customName?: string`。玩家角色使用自定义姓名；普通侠客没有该字段。所有角色名称展示统一采用 `progress.customName ?? definition.name`，覆盖侠客列表、角色详情、阵容选择与战斗单位名称。可选字段使现有 version 10 存档保持兼容，无需迁移。

## 新档创建

新增一个专用的新档创建函数，职责是：

1. 校验并规范化姓名。
2. 从现有 `createInitialStateV10(now)` 创建基础状态。
3. 写入 `heroes.hero_player`，使用 `createHeroProgress('sword')` 初始化成长数据并保存 `customName`。
4. 将 `hero_player` 放入 `{ row: 'front', position: 0 }`。
5. 创建 `GameSession` 并立即保存。

新档仍使用 save version 10。新建游戏只覆盖 `SAVE_KEY_V10` 对应的当前存档，不清理其他 localStorage 数据。

## 姓名规则

- 提交前去除首尾空白。
- 规范化后长度必须为 1～8 个 JavaScript 字符。
- 空姓名或超长姓名不能创建游戏，并在输入框附近显示中文错误。
- 输入内容作为纯文本处理；现有 HTML 渲染链路必须通过 `escapeHtml` 输出。
- 按 Enter 与点击“踏入江湖”执行同一提交逻辑。
- 创建失败后保留输入内容，方便玩家修改或重试。

## 继续游戏

- 只有 `SAVE_KEY_V10` 存在时“继续游戏”才可操作。
- 点击后通过现有存档加载链路创建 `GameSession`。
- 有效旧存档保持原样，不添加 `hero_player`、`customName` 或默认阵容。
- 存档解析或加载失败时不创建新档、不覆盖原存档，标题页显示错误提示。

## 删档重开

游戏侧栏底部新增“删档重开”入口。第一次点击只打开页面内确认区域，明确告知该操作会永久删除当前进度；玩家可以取消或确认。

确认后依次执行：

1. 停止当前战斗与运行时更新。
2. 调用 `clearSaveV10` 删除当前存档。
3. 丢弃当前 session 和页面选择状态。
4. 进入空白的新建游戏页。

如果删除存档抛出异常，则保留当前 session 和游戏页面，显示错误提示，不执行内存重置。删除后的标题状态不得提供“继续游戏”。

## 视觉与交互

标题页和新建游戏页延续现有水墨武侠配色、思源宋体与按钮风格。标题页显示游戏名称、简短副标题以及两个主操作。新建游戏页包含姓名标签、文本输入、校验区域、“踏入江湖”和“返回”按钮。

覆盖存档与删档均使用页面内二次确认，不使用浏览器原生弹窗。危险操作在颜色、文案和按钮顺序上与普通主操作区分。

## 异常处理

- 存档检测失败：标题页继续显示，新建游戏仍可进入，但展示存储不可用提示。
- 继续游戏失败：保留原始存档，停留标题页并提示存档无法读取。
- 新档保存失败：不进入游戏，保留姓名输入和原存档，显示保存失败提示。
- 删档失败：继续保留当前游戏状态，关闭或保留确认区域均可，但必须显示失败提示且不能伪装成功。
- 重复提交：创建过程中暂时禁用提交按钮，避免连续创建多个 session。

## 测试策略

### 单元测试

- 姓名规范化：去除首尾空白、拒绝空名称、拒绝超过 8 个字符。
- 新档生成：包含 `hero_player`、丙级剑客进度、自定义姓名和前排首位阵容。
- 玩家姓名持久化：保存后重新加载仍保持姓名与阵容。
- 旧档兼容：继续有效旧档时不补发玩家角色。
- 角色名称解析：玩家使用 `customName`，普通侠客使用静态定义名称。
- 删档：只删除 `SAVE_KEY_V10`。

### UI 测试

- 标题页在有、无存档时正确启用或禁用“继续游戏”。
- 新建游戏表单显示姓名错误并保留输入。
- 已有存档时显示覆盖确认，取消不会写入。
- 游戏侧栏显示删档入口及页面内确认状态。

### E2E 测试

- 首次启动 → 新建游戏 → 输入姓名 → 进入侠客列表看到玩家 → 第一关可开始挂机。
- 页面重载 → 标题页 → 继续游戏 → 玩家姓名与阵容保持不变。
- 有存档时新建游戏 → 覆盖确认 → 新姓名替换旧进度。
- 游戏内删档 → 确认 → 返回新建游戏页 → 继续游戏不可用。

## 验收标准

- 无存档首次启动不会进入没有角色的空白游戏主体。
- 新档创建后玩家姓名在侠客页和战斗中一致显示。
- 新档无需额外配置阵容即可开始第一关挂机。
- 旧存档通过“继续游戏”保持原状，不获得玩家角色。
- 覆盖和删档均必须显式二次确认。
- 存储操作失败时不会显示虚假的成功状态或丢弃内存中的当前进度。
- 相关单元测试、UI 测试、E2E、`npm run build` 与 `git diff --check` 全部通过。
